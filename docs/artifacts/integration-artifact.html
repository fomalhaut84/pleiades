발견 1

"통합"은 하나가 아니라 두 개의 축이다

축 A — 하네스·세션 통합: Claude Code 를 어떻게 쓰느냐의 문제. 스킬·에이전트·규칙·메모리·세션. 코드는 한 줄도 안 건드린다.

축 B — 코드·제품 통합: 저장소와 런타임의 문제. 공유 패키지, 모노레포, 단일 앱.

두 축은 따로 결정할 수 있다. 축 A 는 축 B 없이도 이득이 나고, 축 B 는 축 A 가 먼저 있으면 훨씬 싸진다. 순서가 정해지는 지점이다.

발견 3

AI 어드바이저 통합은 코드 통합 없이 지금도 된다

두 MCP 서버는 이미 같은 서버에서 로컬 HTTP 로 상주 중이다 (:4210, :4301). mcp-config.json 한 파일에 두 항목을 함께 넣으면, 하나의 Claude 세션이 재무와 건강 데이터를 동시에 본다.

이게 "키운다"의 실체다. 저장소를 합쳐야 얻는 게 아니다. "이번 달 야근이 늘었는데 수면·러닝 부하와 외식비가 같이 어떻게 움직였나" 같은 질문은 두 MCP 를 한 세션에 물리는 순간 답이 가능해진다.

단 001 이 여기 덧붙인 "되돌리기는 JSON 두 줄"은 틀렸다 — 발견 7 참조.

2026-09-04 정정 — "이미 로컬 HTTP 로 상주 중"이 확인되지 않는다. 현재 측정으로 로컬에 pm2 가 설치돼 있지 않고 4210·4301 리슨도 없다. 서버를 기술한 것으로 보이나 확인된 바 없다. 단계 0 착수 전 미결(Q23)이고, 이 발견의 전제가 여기 걸려 있다.
발견 4

알림 채널 교체는 절반만 싸다

아웃바운드(알림 발신)와 인바운드(봇 명령)의 비용이 완전히 다르다. 이걸 구분하지 않으면 비싼 쪽을 두 번 하고 버리게 된다.

아웃바운드 fin 3,378 + fit 1,212줄 · 인바운드 fin 3,968 + fit 1,843줄
전송 호출 fin 149 / fit 61 — 전부 인바운드 쪽에 몰려 있다

아웃바운드는 이미 한 지점을 지난다 — myFinance 는 bot/utils/telegram.ts, myFitness 는 bot/notifications/send.ts. 알림 모듈 16개/5개 중 원시 전송을 직접 하는 건 각각 1개뿐이다. (같은 역할이 다른 파일에 있는 것 — 스킬 이름이 갈린 것과 정확히 같은 쌍둥이 패턴이고, 001 이 측정한 드리프트 142줄이 그 값이다.)

그래서 인바운드를 저장소별로 각각 Discord 로 옮기면 안 된다. 비싼 작업을 두 번 하고, 통합할 때 버린다. 아웃바운드만 먼저 옮기고 인바운드는 단일 봇까지 텔레그램으로 둔다.
