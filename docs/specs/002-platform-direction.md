## 1. 무엇이 바뀌었나

001 은 이렇게 끝났다 — *"B1(공유 패키지)에서 멈추는 게 현실적으로 가장 좋은 종착지일 수 있다.
B2(모노레포)는 '저장소가 둘이라 아프다'가 실제로 관측될 때만."*

그 결론은 **저장소가 영원히 둘**이라는 전제 위에 서 있었다. Q1 의 답이 그 전제를 깬다.

> "지금 재무/건강 관리에서 더 확장될 여지가 있어. 개인 비서 형식으로 확장하고자해.
> 핵심은 각 기능별로 파편화 된 기능을 한곳에 모아두고자 하는거야.
> 그러면 다른 방향으로 확장도 추가 프로젝트 없이 확장 가능할테고
> 그거에 따라서 알림 시스템도 기존 텔레그램에서 디스코드나 슬랙으로 바꾸고자해."
> — 2026-09-03

도메인을 계속 늘리는 것이 목표라면 B2 는 증거를 기다릴 선택지가 아니라 **요구사항 그 자체**다.
B0 에서 도메인 #3 을 붙이면 저장소 하나 + PM2 3개 + 봇 하나 + `logger.ts`·`session-utils.ts`
사본이 또 생긴다. 지금 관측된 드리프트(`session-utils.ts` 44줄 중 22줄 차이)가 3배가 된다.

**다만 가는 길은 그대로 되돌리기 비용 순이다.** 달라지는 건 종착지를 알고 가므로
각 단계를 *모노레포 호환 형태로* 해야 한다는 점뿐이다.

## 2. 확정된 답

| | 질문 | 답 | 근거 |
|---|---|---|---|
| Q1 | "키운다"의 목표 | **개인 비서 플랫폼.** 도메인을 계속 늘린다 | 사용자, 2026-09-03 |
| Q4 | myFitness 테스트 | **붙인다** | 사용자, 2026-09-03 |
| Q5 | 도메인 #3 | **일정·캘린더** | 사용자, 2026-09-03 |
| Q6 | 알림 채널 | **Discord** | 사용자, 2026-09-03 |

**Q5 를 왜 지금 물었나.** N=2 로 만든 추상화는 셋째 도메인에서 거의 깨진다.
"추가 프로젝트 없이 확장 가능"하려면 도메인 모듈 계약이 있어야 하고,
그 계약은 세 번째 도메인이 있어야 검증된다. 일정·캘린더를 고른 이유:

- 001 의 예시 질문 — *"이번 달 야근이 늘었는데 수면·러닝 부하와 외식비가 같이 어떻게 움직였나"* —
  가 실제로 답 가능해지는 유일한 도메인이다. 야근은 캘린더에 있다
- 재무·건강 **양쪽과 모두 교차**한다. 독립 도메인이면 계약 검증에는 깨끗하지만 교차 가치가 없다
- 스키마가 이벤트 시계열이라 기존 둘(거래 시계열 / 활동 시계열)과 형태가 같다.
  도메인 계약이 **`시계열 + 집계 + 알림`** 으로 수렴하는지 검증하기 좋다

## 3. 새 실측 — 알림 채널 교체의 실제 비용

001 작성 시점에는 측정하지 않았던 값이다. 상세 명령은 `../research/measured-facts.md`.

### 발견 4 — 알림 채널 교체는 절반만 싸다

| | 코드 규모 | 전송 호출 | 교체 성격 |
|---|---|---|---|
| **아웃바운드** (알림 발신) | fin 3,378 / fit 1,212줄 | 사실상 초크포인트 1곳 | **어댑터 교체** |
| **인바운드** (봇 명령) | fin 3,968 / fit 1,843줄 | **210건** (fin 149 / fit 61), 파일 30개 | **재작성** |

아웃바운드는 이미 한 지점을 지난다 — myFinance 는 `src/bot/utils/telegram.ts`,
myFitness 는 `src/bot/notifications/send.ts`. 알림 모듈 16개/5개 중 원시 전송을
직접 하는 건 각각 1개뿐이다. *(같은 역할이 다른 파일에 있는 것 — 스킬 이름이 갈린 것과
정확히 같은 쌍둥이 패턴이고, 001 이 측정한 드리프트 142줄이 그 값이다.)*

인바운드는 grammY `Context` 가 명령 파일 30개를 관통한다.

> **그래서 인바운드를 저장소별로 각각 Discord 로 옮기면 안 된다.**
> 비싼 작업을 두 번 하고, 통합할 때 버린다. 아웃바운드만 먼저 옮기고
> 인바운드는 단일 봇(B3 일부)까지 텔레그램으로 둔다.

### 발견 5 — 텔레그램이 `src/bot` 밖으로 새어 있다

채널 교체 시 함께 손대야 하는 곳:

| 저장소 | 파일 |
|---|---|
| 양쪽 공통 | `src/mcp/logger.ts` |

### 발견 6 — 첫 공유 패키지는 Next 16 정렬을 기다릴 필요가 없다

**001 의 선결조건 하나가 걷힌다.** `src/bot` 이 `next` 를 import 하는 건수는 양쪽 다 **0**.
추출 후보 3파일이 사실상 무의존이다:

| 파일 | myFinance | myFitness | 외부 의존 |
|---|---|---|---|
| `bot/utils/error.ts` | 101줄 | 85줄 | **import 0건** |
| `bot/utils/telegram.ts` | 118줄 | 60줄 | grammY + 형제 파일뿐 |
| `bot/notifications/send.ts` | (없음) | 124줄 | grammY + `../utils/error` |

봇은 이미 별도 PM2 프로세스다(`myfinance-bot`, `myfitness-bot`). **오늘 뺄 수 있다.**

### 덤 — 구조가 이미 쌍둥이다

양쪽 모두 `src/bot/{middleware,utils,commands,notifications}` + `standalone.ts` + `src/lib/cron.ts`
레이아웃이 **완전히 동일**하다. 도메인 모듈 계약의 뼈대를 이미 손으로 두 번 그려놨다는 뜻이다.

### 단계 0 · 통합 어드바이저 — *지금, 반나절*

내용은 001 과 같다. **목적이 바뀐다**: "재미있나" → **"비서 프레이밍이 성립하나"**.
캘린더가 도메인 #3 으로 확정됐으므로, 여기서 검증할 것은
"두 도메인을 한 세션이 볼 때 실제로 쓸 만한 답이 나오는가"다.
쓸 만하지 않으면 도메인을 늘리는 것 자체가 무의미하다.

> **멈춰도:** 잃는 것 없음.

### 단계 1 · 알림 어댑터 + Discord 아웃바운드 — *승격*

001 에서는 단계 3(B1) 안에 묻혀 있던 작업을 앞으로 당긴다. 네 가지가 한꺼번에 성립하기 때문이다:

1. 사용자가 **어차피 원하는** 작업이다 (Q6)
2. 아웃바운드는 **이미 초크포인트**다 (발견 4)
3. **Next 무관**이라 정렬을 기다리지 않는다 (발견 6)
4. 추출 패턴의 **파일럿**이다 — 가장 작은 조각으로 B1 방식을 검증한다

**설계.** `@pleiades/notify`:

```
Notifier 인터페이스  ─┬─ TelegramAdapter  (기존 동작 보존)
                     └─ DiscordAdapter   (신규)
```

- 재시도 백오프 · HTML 파싱 실패 시 plain 폴백 · 4096자 분할은
  myFitness `send.ts` 에 이미 있다. 추출 시 양쪽 구현을 비교해 정본을 고른다
- 채널 라우팅은 어댑터 안에 둔다. Discord 서버 하나 + 도메인별 채널
  (`#finance` `#fitness` `#calendar`)
- **선결:** 이 코드에 테스트 (Q4 = 예). **myFitness 의 첫 vitest 도입 지점**이고,
  범위는 추출 대상 코드로만 한정한다. myFitness 전체에 테스트를 붙이는 프로젝트가 아니다

> **멈춰도:** 어댑터 경계가 남는다. 채널 되돌리기는 env 한 줄.

### 단계 2 · 하네스 플러그인 + 메모리 — *유지*

001 의 A1 · A2 그대로. 도메인이 늘수록 가치가 오른다.
단 `MEMORY.md` 200줄 한도가 도메인 3개면 더 빡빡해진다 — 압축 선행은 여전히 필수.

### 단계 3 · Next 16 정렬 + 나머지 공유 패키지 — *유지, 레이아웃만 변경*

MCP 뼈대(`logger`, `session-utils`, HTTP transport), `claude -p` 어드바이저 래퍼.
**이때부터는 모노레포 호환 레이아웃으로 뺀다** — 단계 4 에서 그대로 `packages/*` 가 되도록.
001 과 달리 이 단계는 종착지가 아니라 경유지다.

### 단계 4 · 모노레포 (B2) — *진입 조건 변경*

| | 001 | 002 |
|---|---|---|
| 진입 조건 | 크로스 저장소 변경이 월 2회 이상 | **도메인 #3(캘린더)을 실제로 붙일 때** |
| 성격 | 증거가 나오면 하는 선택 | 목표에 내장된 요구사항 |

`apps/{finance,fitness,calendar}` + `packages/{notify,mcp-core,advisor}`.
**여기서의 진짜 산출물은 폴더 구조가 아니라 도메인 모듈 계약이다** —
새 도메인이 무엇을 구현하면 플랫폼에 꽂히는가: DB 스키마 / MCP 도구 / 알림 라우트 /
스케줄 잡 / UI 라우트. 계약 없는 모노레포는 두 앱을 한 폴더에 넣은 것일 뿐이다.

## 5. B3 는 쪼갠다
