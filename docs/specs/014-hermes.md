## 1. 무엇을 만드나

```
[외부 앱]  ─┐ HTTPS(B2 · 나중) / 루프백(B1)
[내부 앱]  ─┼─▶ hermes  ──▶ 대기열(디스크) ──▶ 게시 루프 ──▶ Discord #spot (웹훅 하나)
[주기 작업]─┘   ① 인증(출처 키)          ② 검사 · 형식          ③ 재시도 · dead
                                                         └─▶ 수집기가 상태를 읽어 #ops 로(감시)
```

- **받는다:** `POST /v1/messages` 하나(§2). 출처는 **키로 정한다** — 본문의 이름을 믿지 않는다.
- **적는다:** 받은 즉시 디스크 대기열에 쓰고 `202` 로 답한다. 이 시점부터 유실 책임은 hermes 다.
- **보낸다:** 게시 루프가 대기열을 읽어 검사(§3-F) · 형식(§3-E) 뒤 웹훅으로 보낸다. 실패는 백오프로 재시도 · 한도를 넘으면 `dead`.
- **알린다:** 검사 차단은 그 메시지 자리에 **고정 문구만 `#spot` 에**(§3-F · 출처 주인이 "안 왔다" 를 본다) · dead · 차단 **건수** · 대기열 적체 · 웹훅 없음은 **수집기가 `#ops` 로**(§3-G) — 출처의 소음과 운영 신호를 섞지 않는다(D5 의 이유와 같다).

**hermes 가 하지 않는 것:** 양방향(D3) · 출처별 채널 분기(D4 — 필요해지면 §8 Q-H7) · 첨부 파일 · 앱 알림(`ALLOWED`·`ADMIN` 라우트는 notify 그대로 · D5) · 주기 작업 실행(크론은 작업 쪽이 돈다 — hermes 는 받기만).

## 2. API v1 (초안)

```
POST /v1/messages
Authorization: Bearer <출처 키>
Content-Type: application/json
Idempotency-Key: <출처가 정한 문자열 · 선택 · 최대 128자>

{
  "title": "새 주문",                       // 선택 · 최대 100자 · 한 줄
  "text":  "주문 #123 · 5kg × 2 · 58,000원", // 필수 · 최대 1500자
  "link":  { "label": "주문 보기", "url": "https://…" },  // 선택 · 1개(D3) · https 만 · 출처별 허용 호스트(§3-D)
  "level": "info"                          // 선택 · info | warn · 기본 info
}
```

| 응답 | 뜻 | 보내는 쪽이 할 일 |
|---|---|---|
| `202 {"id","duplicate":false}` | 대기열에 적었다 | 끝 |
| `202 {"id","duplicate":true}` | 같은 `Idempotency-Key` 를 이미 받았다(보존 창 안) | 끝 |
| `400` | 형식 오류(필드 · 길이 · `link` 스킴) — 사유 코드만 | 고치기 전에는 재시도하지 않는다 |
| `401` | 키 없음·틀림 | 재시도하지 않는다 |
| `403` | 출처가 꺼졌거나 만료(§3-D) | 재시도하지 않는다 |
| `413` | 본문 바이트 상한 초과(예: 16 KB) | 재시도하지 않는다 |
| `429` + `Retry-After` | 출처별 속도 제한 | 그 뒤 재시도 |
| `503` | 대기열 쓰기 실패 · 종료 중 | **재시도한다** |
| 연결 실패 · 시간 초과 | hermes 가 죽어 있다 | **재시도한다**(같은 `Idempotency-Key`) |

- **보내는 쪽의 재시도는 계약이다.** hermes 가 죽어 있는 동안 온 요청은 hermes 의 대기열이 받을 수 없다 — 무엇을 대기열로 두든(§3-C) 이 구간은 **보내는 쪽 재시도 + `Idempotency-Key` 중복 제거**로만 덮인다.
- **검사 차단(§3-F)은 응답에 드러나지 않는다** — 받은 뒤 게시 루프에서 걸러진다(`202`). `#spot` 의 고정 문구가 사유 코드(`length`·`token`·`secret-match`·`pii`)만 보이고 **원문·규칙·걸린 값은 어디에도 노출하지 않는다** — 차단을 완전히 숨기지는 않되(출처 주인이 알아야 한다) 우회 단서를 줄인다(008 §5-1 "우회 학습 경로" 의 낮춘 적용). 차단 건수는 수집기가 `#ops` 로 낸다.
- `GET /v1/health` — 인증 없음 · `{"ok":true}` 뿐(대기열 수치는 상태 파일로 · 수집기가 읽는다). "루프백에서만" 은 B1 에서만 참이다 — B2 의 nginx 도 루프백에서 오므로 **nginx 쪽에서 `/hermes/v1/health` 를 막는다**(H-5 런북).
- 버전은 경로(`/v1`)로 — 바꾸면 `/v2` 를 같이 둔다.

**Discord 로 나가는 모양(§3-E):** 웹훅 `username` = 출처의 표시 이름(레지스트리) · 본문 = `**title**` 줄 + `text` + 링크 줄(`label` + 주소가 보이는 형태 · 013 R2) · `level=warn` 은 앞에 ⚠️ · `allowed_mentions: { parse: [] }`(N3).

**권고 C3.** 이유:
1. **유실의 두 구간 중 하나만 대기열이 덮는다**(§2): 출처 → hermes 구간은 무엇을 두든 보내는 쪽 재시도가 덮는다. Kafka 를 둬도 hermes 입구가 죽어 있으면 그 사이 요청은 받지 못한다.
2. hermes → Discord 구간은 **받은 즉시 커밋 → 게시 루프 → 성공 표시**의 outbox 로 충분하다. 브로커가 주는 것(분산 · 재생 · 다수 소비자)은 소비자가 hermes 하나라 쓰이지 않는다.
3. 새 데몬 0 · 되돌리기 **즉시**. **백업은 지금 없다** — `db-backup.cjs` 는 pg_dump 만 한다(N20). 대기열은 30일 보존의 전달 버퍼라 백업 대상으로 두지 않는다 · 필요해지면 `VACUUM INTO`(WAL 중 파일 복사는 일관된 사본이 아니다).

**교체 자리:** 대기열은 인터페이스(`enqueue` · `claimNext` · `markSent` · `markRetry` · `markDead` · `purge`) 뒤에 둔다 — 처리량이 필요해지면 C4·C5 로 갈아 끼운다(§9 유효기간).

**`node:sqlite` 의 조건(D10 확정 뒤):** node 22.5+ 에만 있다 — 서버 · CI 는 24 · 로컬은 셸 기본이 20.18 이라 **H-1 이 node 24 를 고정한다**(N12 · `engines` + `run.sh hrm` 의 node 경로 확인). 실험 기능 경고는 node 22 실측 · 로컬 24.22 는 없음 · 서버 24.12 에서 나오면 `--disable-warning=ExperimentalWarning`(D10 · 수집기 분류표는 건드리지 않는다). 막히면 대안은 ② `better-sqlite3`(네이티브 빌드) ③ C2 — 그때 D10 을 다시 연다.

**동작 규칙(C3 기준):**
- 받기: 한 트랜잭션에 행 삽입(`queued`) → 커밋 → `202`. `Idempotency-Key` 는 (출처, 키) 유일 · 보존 창 7일(설계 변수).
- 게시: 한 번에 하나 · 순서 = 받은 순서(출처 사이 공정성은 속도 제한이 맡는다) · Discord `429` 는 `retry_after` 를 따른다 · `5xx`·연결 실패는 지수 백오프(예: 5 s → 10 m 상한) · **시도 N회(예: 20) 또는 경과 24 h → `dead`**.
- 게시 성공 판정은 `?wait=true` 응답(수집기 PR #726 Codex P2 와 같은 이유 — 없으면 저장 못 한 메시지에도 성공).
- 보존: `sent` · `blocked` · `dead` 는 30일 뒤 삭제(설계 변수) — **본문을 오래 두지 않는다**(§3-I).
- 웹훅 키가 없으면(`DISCORD_WEBHOOK_SPOT` 비어 있음) 받기는 계속하고 게시는 멈춘다 — 수집기가 "웹훅 없음" 을 `#ops` 로.

### 3-D. 출처 · 인증

| | 내용 | 되돌리기 |

- **만료(`expires`)** 가 한시 출처의 본체다 — 시즌이 끝나면 따로 지우지 않아도 `403`. 만료 7일 전 · 만료 당일 수집기가 `#ops` 일일 요약에 한 줄(§3-G).

- 내부 앱도 **같은 방식으로 키를 받는다** — 루프백이어도 키 없이 받지 않는다(같은 서버의 다른 프로세스가 출처를 사칭하지 못하게 · B2 로 열 때 예외를 지우는 일이 생기지 않게).

### 3-G. 감시

- hermes 는 상태 파일(`state.json` · 상태 디렉터리)에 **수치만** 쓴다: `queued` · `dead`(누적·오늘) · `blocked`(오늘) · 마지막 게시 성공 시각 · 웹훅 유무 · 만료 임박 출처 id.
- **수집기**가 넷째 체크아웃이 있을 때만 `pleiades-hrm-*` 를 감시 대상에 넣는다(N6 의 adv 방식) — pm2 상태 · 재시작 · `-error` 로그 패턴 · 위 상태 파일. `dead` 증가 · 적체(`queued` 가 N분 이상 줄지 않음) · 웹훅 없음 → `#ops` 경고 · 만료 임박 → 일일 요약 한 줄.
- **"`activeApps` 에 한 줄" 로 끝나지 않는다(N16):** `APP_DIRS`·`ROLES_OF` 에 hrm · 로그 이름 정규식의 앱 칸과 **역할 칸**(`api` · D9) · 활성 표지(`inplace-hrm-last-ok`·`-stopped` — hermes 배포 스크립트가 같은 규약으로 쓴다) · 배포 창 표지(`inplace-hrm-pending`·`-window` — 배포 중 보류) · **봇 생존 표지 판정에서 hrm 제외**(hermes 는 gateway 봇이 아니다) · 상태 파일 판정 신설 · `test_ops_collect.py` 갱신 · **수집기 재설치**(사용자).
- hermes 자신은 `#ops`·`#admin` 에 쓰지 않는다(D5 · 웹훅 하나 원칙 D4).

### 3-H. 내부 출처의 연결 (D2 ②③)

| | 내용 | 되돌리기 |
|---|---|---|
| **H1 ★** 같은 HTTP API(루프백) + 출처 키 | 내부 앱·작업도 외부와 같은 길 · 클라이언트는 `fetch` 몇 줄 | — |
| H2 얇은 클라이언트 `packages/hermes-client` | 재시도 · `Idempotency-Key` · 키를 플랫폼 설정에서 읽기 | 패키지 삭제 **중간** — **내부 출처가 둘 이상일 때**(§8 Q-H2) |
| H3 내부 앱이 대기열(`hermes.db`)에 직접 쓴다 | HTTP 없음 | 스키마가 공개 인터페이스가 된다 · 검사·인증 우회 — 택하지 않는다 |

- **내부 출처 키의 자리:** 플랫폼 설정의 새 키(예: `HERMES_KEY_<출처>`)는 지금 `PLATFORM_KEY_RE`(N1)에 없다 — 넣으면 notify 공개 인터페이스(정규식) 변경이다. 대안: 그 앱의 `.env`(앱 비밀과 같은 자리 · `check_env.py` 의 "앱 `.env` 에 플랫폼 키 금지"(:258-259)와 충돌하지 않는다). 수집기 ① `SECRET_KEY` 의 `_KEY` 접미가 그 키를 잡지만 **대조 재료는 fin·fit `.env` + 플랫폼 설정뿐**이다(N5) — adv 나 새 작업 앱의 `.env` 에 둔 키는 수집기 ① 이 모른다. 그래서 **출처 키 형식을 ② 일반 토큰 검사가 잡는 모양으로 고정**한다 — 수집기 `isGenericToken`(`collect.cjs:845`)은 **16진수만으로 된 문자열을 뺀다**(커밋 해시 오탐 방지)·숫자와 영문을 모두 요구·`-`/`_` 로 나눈 조각 중 가장 긴 것이 `MIN_TOKEN_PIECE` 이상이어야 한다. 그러므로 키 = **접두 `hrm_` + base62 43자**(16진수 밖 글자 `g-z`·`G-Z` 가 들어가지 않으면 다시 뽑는다 · 숫자·영문 둘 다 · 구분자 없는 한 조각) — `hermes-key.sh` 가 이 규칙으로만 만들고 레지스트리 로더가 해시 전 평문 검사를 하지 못하므로 **생성 쪽 시험**(만든 키 N개가 전부 `isGenericToken` 참)과 **`token_vectors.json` 에 `hrm_` 키 벡터(잡힘) + 64자 hex(안 잡힘 — 이 형식을 쓰면 안 되는 이유)를 더한다**(정정 #761 · Codex P2). **권고: 앱 `.env` + 그 키 형식**(§8 Q-H2).
- **pleiades 안의 주기 작업이 어디 사는가**(새 `apps/<작업>` · `jobs/` · 기존 앱의 크론)는 이 문서 범위 밖 — 작업이 처음 생길 때 정한다. 이 문서가 정하는 것은 **"작업은 hermes API 로 보낸다"** 하나다.

### 3-I. 개인정보 · 보존

- **원칙: `#spot` 에는 사람을 특정하는 값을 보내지 않는다** — 이름 · 주소 · 전화 · 이메일 · 계좌. 주문 알림은 *주문 번호 · 수량 · 금액 · 상태* 와 관리 화면 링크까지. Discord 메시지는 지워도 알림·검색에 남는다.
- hermes 는 **전화번호 · 이메일 패턴을 F1 에서 차단한다**(D11 · 사유 `pii`) — 이름 · 주소 같은 문맥 판단이 필요한 값은 기계로 못 잡으므로 출처 등록 런북의 체크 항목으로 둔다. 패턴의 거짓 차단(주문 번호 · 금액 · 날짜가 전화번호처럼 보이는 경우)을 `clean` 벡터로 시험한다.
- hermes 는 본문을 대기열 보존 기간(§3-C · 30일)만 둔다 · 로그에는 본문을 쓰지 않는다(출처 id · 길이 · 결과만).

## 5. 임시 경로 (첫 출처가 hermes 보다 먼저 시즌을 시작할 때)

1. 사용자가 Discord 에 `#spot` 채널과 **임시 웹훅 하나**를 만든다(hermes 가 쓸 웹훅과 **다른** 웹훅).
2. 주문 앱은 그 웹훅으로 직접 보낸다. 앱 안의 메시지는 처음부터 **§2 필드(title · text · link 하나 · level)로 만들고, 보내는 곳마다 직렬화기를 둔다**:
   - **Discord 직렬화기(임시):** `{ content, allowed_mentions: { parse: [] } }` — `content` = §3-E 와 같은 모양(굵은 제목 줄 + 평문 text + `🔗 label · url` 줄 · 2000자) · text 의 서식 문자 escape 는 출처 몫(이 구간에는 §3-F 검사가 없다)
   - **hermes 직렬화기:** §2 JSON 그대로 + `Authorization` + `Idempotency-Key`
   - 두 요청은 본문 모양이 다르다 — **Discord 요청을 hermes 로 보내면 `400`, §2 JSON 을 웹훅으로 보내면 Discord 가 거부한다.** §3-I 를 지킨다.
3. hermes 가 서면 주문 앱은 **직렬화기를 hermes 쪽으로 바꾸고 URL · 키를 넣는다**(재시도 · `Idempotency-Key` 는 §2 계약 — 임시 경로에는 없던 것) → hermes 로 한 건 보내 `#spot` 에 보이는지 확인 → 사용자가 임시 웹훅을 삭제한다(**즉시**).

pleiades 쪽 작업 0 · 이 경로 동안은 §3-F 검사가 없다(출처 책임). 출처 쪽 작업 = 직렬화기 둘(교체는 설정 · 코드 분기 하나).

## 7. 판단 근거 요약 — 왜 웹훅 직접이 아니라 중계인가
