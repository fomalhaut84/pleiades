### 2-1. 축별 보충

**A1 의 힌트 범위.** 4b(새 채널)에서는 힌트가 없다 — 두 도메인 지식을 모두 싣는다(확인된 소계 [N10] · 미확인 포함 시 더 크다). 지식 싣기의 비용은 미측정(§0-4)이므로 4b 로그로 보고, 도메인 #3 이 붙을 때(셋째 지식) 힌트별 선택(힌트 도메인 전체 + 나머지 요약)을 다시 판단한다. 되돌리기: 설정 **즉시**.

**B1 = 단위, 프로세스 아님.** 도메인 에이전트를 프로세스나 서브에이전트로 나누면 H2·H3 의 지연이 붙는다(011 §4-8). 지금 B1 이 하는 일은 "계약 v0 이 도메인 단위로 정의되고 · 지식·기억이 도메인 키로 나뉜다" 이다.

**C3+ 엔드포인트가 분류 파싱을 대체한다.** X1 은 배포 체크아웃의 분류 소스를 텍스트로 파싱했다(`judge.cjs` `finLists`·`fitLists` · RT §6). 4a 의 읽기 전용 엔드포인트는 **읽기 도구만 등록**하므로, 통합 층은 그 엔드포인트의 `tools/list` 를 허용 목록으로 쓰고 쓰기 도구는 **존재하지 않는다**(settings allow 가 있어도 부를 대상이 없다 · 011 C3+ 이득). 통합 층과 앱의 버전이 어긋나도(배포 시점 차) 목록은 늘 배포된 MCP 가 정한다. **분류 오류는 그대로 열린다**(같은 분류로 등록을 거르므로 · R-1).

### 5-3. 계정 공유 맥락 (UI)

## 12. 감사가 반증해 볼 주장 (싸다고 한 곳 위주)

1. **G7 이 두 운영 앱의 배포 경로를 건드리지 않는다** — `ssh-deploy.sh` 한 단계 추가가 forced command 경로(fin 체크아웃 안 파일)·배포 알림(`notify-deploy.cjs`)·`release-inplace.sh` C1 의 `pleiades-*` 프로세스 검사(`PLEIADES_ENV_FILE` 일치 · 프로세스 수 `3`)에 정말 무해한가. 셋째 pm2 이름이 C1 검사에 걸리면 **fin·fit 배포가 멈춘다.**
2. **G7·G1′ 의 릴리즈 종류(minor 후보)** — "셋째 체크아웃이 없으면 건너뛴다" 가 #199 의 major 정의(체크아웃·상태 경로 구조 변경)를 피하는가.
3. **C3+ 가 앱당 [N8] 지점으로 끝난다** — 별도 경로의 sid 모드 가드 · stdio 경로(fit `MCP_TRANSPORT=stdio` 회귀 경로) · 계측 래퍼에서 등록을 건너뛸 때 SDK 가 빈 이름을 어떻게 다루는가 · 배포 pre-flight(`deploy.sh` MCP 확인)가 `/mcp` 만 보는가.
4. **읽기 경로의 `tools/list` 가 분류 파싱을 대체한다** — 통합 층이 "쓰기 도구가 없다" 를 확인할 수단(전체 경로 목록과의 차)을 잃지 않는가 · J2 형 사후 판정을 상주에서 어떻게 남기나.
5. **K-3 를 MCP 로 내는 것이 싸다** — SDK 지원 미측정 · fit DB 활성 본문 크기 미측정 · fin 지식 이전(K2)이 TA 가이드·active review 답을 바꾸지 않는다는 주장은 판정 양식 전에는 근거가 없다.
6. **4c-1 이 분기 2 + 정규식 1** — fin `isAiQuestion` 공용화(4c-2)가 fin 의 소비 판정 순서와 경쟁하지 않는가(같은 메시지를 앱 봇은 소비로, 통합 봇은 질문으로) · 플랫폼 env 재읽기가 앱 봇 프로세스에서 실제로 메시지마다 일어나는가.
7. **(b1) 기억이 서버 조치 0** — 비공개 위치 규칙 재사용이 서버 디렉터리 권한·백업 정책과 충돌하지 않는가 · 서버를 잃을 때 기억 손실을 사용자가 받아들이는가.
8. **[D2] $3.00 이 여유 있다** — P1·P2 는 X1(새 세션 · 단발)에서 나온 값이고 resume 대화·지식 싣기 비용은 미측정이다.
