## 3. 실측 근거 (코드 · `apps/finance` · `dev` 0740ada)

### 3-1. 경계는 "보유 종목만" 이다

- 스냅샷 평가액 = 보유 종목 평가액의 합 · 현금 없음 · 시세가 없으면 평단가(`src/lib/performance/snapshot.ts:40·52`).
- 스냅샷 경로 둘: 크론 **06:05 KST 월~토**(`src/lib/cron.ts:118~127`) · 웹 버튼 POST(`api/performance/snapshots/route.ts:110~112` · `PerformanceClient.tsx:115`). **수동 POST 는 그날 스냅샷을 아무 시각에나 덮어쓰고 그 시각은 남지 않는다**(upsert · `PortfolioSnapshot` 에 `updatedAt` 없음 · `schema.prisma:190~201` · `createdAt` 은 **처음 만든 시각으로 남는다** — 덮어쓴 시각으로 읽지 않는다).
- 보유 수량을 바꾸는 경로 넷 — 모두 `Trade` 로 다시 계산한다: 거래 서비스(웹·봇 · `trade-service.ts`) · 거래 import(`api/trades/import/route.ts`) · RSU vest(웹·MCP · `rsu-vest-service.ts`) · **거래 수정·삭제**(`api/trades/[id]/route.ts:130·168`). 수정·삭제는 과거 기록을 바꾼다.
- `Trade.type` 입력은 BUY·SELL 뿐(`trade-utils.ts` zod · `trade-service.ts:15`). 분할·이체 경로 없음. RSU vest = vest 가격의 BUY(+자동 매도면 SELL).
- `Deposit` 은 1원 이상만(POST·PUT·MCP) · 출금 기록 불가 · **증여 추적용 기록**이다(`deposits/route.ts:121` 증여 한도 검사 · MCP 경로는 `assetId` 만이라 계좌 TWR 에 안 걸린다).
- 기준선 `Trade`: 거래 0건 보유에 첫 거래가 생길 때 1일 전 날짜로 합성(`trade-service.ts:136~151` · import `route.ts:184~214`) — 지금 코드에는 거래 없이 보유를 만드는 경로가 없어 옛 데이터에서만 생긴다. 시드는 `'초기 보유분'` 거래를 고정 날짜로 만든다(`prisma/seed.ts:56~70`).
- 배당: 현금 기록 · 보유 평가액에 안 들어간다 · `reinvested` 는 플래그뿐(재매수 거래 자동 생성 0).

### 3-2. 지금 계산 두 개

| | 식 | 외부 흐름 | 결함 |
|---|---|---|---|
| **기여도** (`contribution.ts:139`) | `(V_end_i − V_start_i) / V_start_i` | 없음 | 매수는 수익, 매도는 손실(#262) |
| **TWR** (`twr.ts:61~99`) | 하위 구간 `(V_end − CF) / V_start − 1` 의 곱 | **`Deposit` 만**(주석 `:19~22` 의 "입금+매수−매도" 와 코드가 다르다) | 경계가 보유 종목뿐이라 **매매가 곧 외부 흐름**이다 — vest·입금 없는 매수는 수익, 매도는 손실 · 입금일 ≠ 매수일이면 입금은 손실·매수는 수익으로 갈린다 · Deposit 은 증여 기록이지 계좌 흐름 기록이 아니다 |

**알파(= TWR − 벤치마크)도 같이 흔들린다.** 운영 데이터에서 얼마나 틀렸는지는 측정하지 않았다(운영 DB 를 읽지 않는다 · I-7 · §6 Q8).

### 3-3. `Trade` 날짜와 스냅샷이 맞지 않는다

- `tradedAt`: 웹 폼·수정·import·vest = **UTC 00:00**(KST 날짜와 같은 날) · 봇 = **입력 순간**(`bot/commands/trade.ts:356` · `ai.ts:432`).
- 거래는 **거래 입력 시점(`Trade.createdAt`) 뒤의 첫 스냅샷부터** 보유에 나타난다. 과거 날짜 소급 입력 · 이력 import · 수정·삭제 · 기준선은 흐름 날짜(`tradedAt`)와 스냅샷이 어긋난다 — 어떤 날짜 경계 규칙으로도 다 맞출 수 없다.
- 예: KST 00:00~06:05 봇 거래(미국장)는 KST 날짜 D 인데 D 06:05 스냅샷에 이미 있다 · 3주 전 거래를 오늘 입력하면 스냅샷에는 오늘부터 나타나지만 `tradedAt` 은 3주 전이다.

## 4. 경로

### 4-1. 보정 식 — Modified Dietz(보유 경계)

기간 [S, E] · 일수 T · 흐름 시점 t 의 가중치 `w_t = (E − t) / T` · 흐름 `CF`(유입 +).

- 종목 i 손익 `G_i = V_end_i − V_start_i − CF_i (+ 배당_i, Q3)`
- 계좌 분모 `D = V_start + Σ_t w_t · CF_t`
- **기여도 `c_i = G_i / D`** · **계좌 수익률 `R = Σ c_i`** — 종목 집합이 **기간 안 스냅샷 전체의 티커 ∪ 기간 배당 티커**면(양 끝만이 아니라 · 매도 뒤 지급되는 배당 포함) 합이 정확히 맞는다(`totalValueKRW = Σ valueKRW` · `snapshot.ts:52`)
- **R 은 Modified Dietz 수익률이지 TWR 이 아니다** — 웹(TWR 카드 · 기여도 "전체" `ContributionTable.tsx:62~63`)과 MCP(TWR `performance.ts:50` · "전체 수익률" `:68`)가 둘을 나란히 낸다. A2 뒤에도 두 숫자는 같아지지 않는다(Q2)
- 종목 수익률(표시) `r_i = G_i / (V_start_i + Σ_t w_t · CF_{i,t})`
- **D 도 작아질 수 있다** — 기간 초 큰 매도면 0 에 가깝거나 음수(예: V_start 1000 · 1일차 900 매도 · T=30 → D≈130). 하한은 Q5.

### 4-2. 흐름을 어디서 얻나 — 핵심 선택

| 안 | 흐름 | 맞는 것 | 틀리는 것 | 되돌리기 |
|---|---|---|---|---|
| **F-t** | `Trade` 의 `totalKRW` · `tradedAt` | 거래 가격이 정확 | §3-3 날짜 어긋남(소급·import·수정·봇 시각) · 기준선·`'초기 보유분'` 합성 거래 | 즉시 ~ 중간 |
| **F-s** (권고) | **연속 스냅샷 사이의 수량 차분** `ΔN_i,k × 가격` — 가격 = **원화 단가 `valueKRW / shares`**(그 스냅샷 환율 포함 · `price` 는 현지 통화라 그대로 쓰면 USD 흐름이 ≈1/1400 이 된다 · `format.ts:105~106`)의 두 스냅샷 평균(Q9) · 시점 = 뒤 스냅샷 날짜 | 스냅샷과 **늘 같은 시점**(소급·import·수정·합성 거래·봇 시각 무관) · vest 포함 · 끝점 수량이 같아도 중간 매매를 잡는다 · 티커 변경·수동 덮어쓰기에도 차분이 깨지지 않는다(감사 2회) | 오차 = 거래 수량 × (체결가 − 사용 가격) — 양쪽 스냅샷이 있으면 대개 구간 변동의 절반 이내지만 **구간은 1~2일 이상**(토→월 · 크론 누락) · **신규·전량 매도 구간은 한쪽 가격만**(전량 매도면 보유 행이 지워진다 · 규칙은 A1-1) · 시세 없어 평단가로 대체된 날은 흐름 가격도 평단가(USD 에 `avgPriceFx` 없으면 0 · `snapshot.ts:40`) · 두 스냅샷 사이 사고 다 판 것은 안 보인다 · 분할도 흐름으로 보인다(기록 경로가 없어 어느 안이든 못 가린다) | 즉시 ~ 중간 |

F-s 는 기간 안 스냅샷을 **전부** 읽는다(지금 기여도는 양 끝 2개 + Trade 1회 · TWR 은 전부를 두 필드만). 월~토라 1Y ≈ 313개 × 보유 종목 수 · **ALL 은 상한이 없다**(`constants.ts:14·21~23`) · MCP "전체" 는 계좌 수만큼 병렬 · A2 면 TWR 도 보유를 읽는다. **측정하지 않았다** — A1-1 에서 로컬 시드로 **ALL × 계좌 수 × (기여도 + TWR)** 로 잰다.

**따로 남는 결함(계산 방식 무관).** 티커 정정 마이그레이션 `20261019090100` 은 과거 스냅샷의 `price`·`valueKRW` 를 일부러 남겼다(주석 "별도 판단") — 2026-10-19 를 걸친 기간은 그 종목에 ΔN=0 가격 점프가 생긴다. 운영 크기는 미확인.

## 5. 판단이 바뀐 것

- **"기여도만 고치면 된다"(#262)** → TWR 도 같은 경계 문제(§3-2).
- **"흐름 = `Trade`"(초안 1)** → 스냅샷 차분(§3-3 · §4-2). 거래 기록은 시점이 스냅샷과 맞지 않는다.
- **B 표시**: F-s 에서는 수량 변동이 곧 흐름이라 "보정되지 않은 변동" 이 없다(분할 제외). 남길지는 Q2.

| Q10 | 웹 성과 차트 · 일일 요약 "전일 대비" 도 고치나 | 같은 결함이 남는 곳(§3-4). 권고: **이 문서 밖 별건**(차트는 기간 TWR 누적선으로 · 일일 요약은 하루 흐름 차감) — A1 뒤 | 낮음 |

(초안 1 의 Q4 기준선은 F-s 를 고르면 사라진다. Q7 날짜 경계는 거래에서는 사라지지만 Q3 을 넣으면 배당 `payDate` 배정으로 남는다 — F-t 를 고르면 둘 다 되살린다.)

## 7. 유효기간

- 스냅샷에 현금 잔고가 들어오면(A3 이 가능해지면) 다시 연다 — 그때는 계좌 경계 TWR 이 맞아진다.
- `Trade.type` 에 분할·이체가 생기면 F-s 의 분할 오인과 B 표시를 다시 본다.
- 스냅샷 주기가 바뀌면(하루 여러 개 · 장중) F-s 의 가격·시점 근사를 다시 본다.
